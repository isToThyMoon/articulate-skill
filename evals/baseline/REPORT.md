# 基线对照：有 skill vs 无 skill

## 目的

检验 skill 相对“直接问模型”是否带来可观察的差别，并检查非 UI 领域中是否有领域特化残留。

## 设置

- 每个场景两个条件：无 skill / 读取本仓库 skill。每次都是新的子 agent，离线、不读其他文件。
- 盲评：独立评审 agent 读取打乱标签的 A/B 文件，按 7 项、每项 0–2 分打分并引用原文。
- 同一模型，每个条件只跑一次。这是小样本观察，不是统计结论。

| 场景 | 请求 | 无 skill | 有 skill（最终文本） |
|---|---|---|---|
| clarify 直接整理（UI） | “首页更高级，别追问，直接给 Agent 要求” | [baseline](clarify-direct-baseline.md) | [final](clarify-direct-skill.md) |
| clarify 直接整理（写作） | “产品发布文章读起来很平，别追问，直接给要求” | [baseline](clarify-writing-baseline.md) | [final](clarify-writing-skill.md) |
| clarify 验收 | 按要求验收结账页改版，“达标没有” | [baseline](verify-baseline.md) | [final](verify-skill.md) |
| deconstruct（UI） | 简短拆解一句含“渐进披露”的评审 | [baseline](deconstruct-ui-baseline.md) | [final](deconstruct-ui-skill.md) |
| deconstruct（代码） | 简短拆解一句关于幂等、去重、竞态的代码评审 | [baseline](deconstruct-code-baseline.md) | [final](deconstruct-code-skill.md) |
| clarify 追问模式 | “App 首页感觉很乱，帮我说清楚，最后交给 Agent 改” | — | [final](clarify-grill-skill.md)（未对照，单独检查：一问、三个候选解释各附专业叫法、说明选择的影响） |
| orient（园艺） | 阳台种菜新手：紧凑地图 + 按依赖排核心概念，为向 Agent 提问和判断建议 | [baseline](orient-garden-baseline.md) | [final](orient-garden-skill.md) |

带 `-first`、`-prev`、`-v2`、`-v3`、`-v4` 后缀的文件是修订过程中的早期输出。

## 结果（最终文本，盲评总分，满分 14）

| 场景 | 无 skill | 有 skill | 字数 无 / 有 | 关键差别 |
|---|---:|---:|---:|---|
| clarify 直接整理（UI） | 5 | 13 | 1626 / 565 | 无 skill 把默认的极简风格和无来历的硬性数值写成定案，点名排除 7 次以上；skill 把“高级”留作待定方向，一段交付 |
| clarify 直接整理（写作） | 5 | 14 | 1311 / 698 | 无 skill 未见原文即断定问题、定下写法；skill 先诊断，标明假设 |
| clarify 验收 | 9 | 12 | 1548 / 1908 | skill 区分证据与推断，每条修复附验收办法，新数值标为建议 |
| deconstruct（UI） | 12 | 14 | 1222 / 993 | skill 指出“低频”缺依据，并给出不适用条件 |
| deconstruct（代码） | 11 | 13 | 1338 / 1449 | skill 指出“客户端带 idempotency key”不适用于支付回调，并标明推断 |
| orient（园艺） | 8 | 13 | 3104 / 2408 | skill 标明证据身份，概念顺序给出理由并区分真实依赖与教学安排；按所列交付物交付 |

评分项：意图保留、范围纪律、证据身份、可执行与可验收（orient 为服务用户目的与概念顺序）、正向表达、领域价值（orient 为领域准确性）、简洁可用。

同一份基线在不同评审轮次中分数波动约 1–3 分，单次差距 2 分以内不稳定。

剩余观察：skill 输出仍有固定开场或收尾句（如“这段评审要解决的问题是”“范围说明（暂定）”），评审视为轻度模板痕迹；验收场景比基线长 23%，主要来自每条修改要求的验收办法。

## 修订要点

- **可移交规则具体化**：抽象规则未能阻止产出点名排除选项，改为“想避开的做法，改写成它会破坏的目标状态”，并在 clarify 的评价词段给出写法。
- **去领域特化**：会装载的文本中，UI 例子换成跨领域或结构性表述（clarify 例子改为接口健壮性，来源表举多领域产物，案例评价改为通用句式）。非 UI 的写作与园艺场景未出现 UI 词汇。
- **去内部术语外泄**：方法名、类别名、流程链与检查标准统一为“整理与自查工具，交付时用领域自己的内容和普通说法”；案例流程由标签链改写为叙述句，消除被照搬为小标题的来源。
- **orient 导航增加提问要素**：向 Agent 提问应交代的条件，以及判断回答可靠的信号。
- **clarify 重构为任务建模**：描述与开头改为“任务建模”；追问时用八类找缺口、候选解释附专业叫法、用五层讲清选中概念；任务说明按八类组织，外加目标与优先级、依据与未知项，取代 O/D/C/M/F 表。三个 skill 的描述统一为“角色：何时用，用八类/五层做什么”。clarify 两个直接整理场景在此之后重跑并重新盲评。
- **orient 按所列交付物交付**：用户列出具体交付物时，贯穿案例改为导航中的一句邀请。
- **篇幅**：foundation 加入“篇幅跟随请求、每条信息只出现一次、交付前删去不改变理解的句子”；orient 紧凑模式与 clarify 修改要求改为可数的限制。
- **deconstruct 去固定结构与方法用语**：变化情境和 Agent 表达改为整体一份；内部措辞由“判断”改为“结论”，步骤名同样归入“整理与自查工具”。
- **清理 skill 包**：删除因单次失败而加的补丁句、解释来历的句子和重复规则；`DESIGN.md` 与历史测试移出 skill 目录（`docs/orient-design.md`、`evals/orient/`）。

## 局限

- 每格只跑一次，模型波动与跨模型差异未测。
- 评审也是模型，评分标准由维护者制定，与 skill 写作目标同源，存在偏向 skill 的风险。
- 未覆盖联网来源获取与知识库读写。
- 对照的是“无 skill”，不是“照原文方法论手写 prompt”；后者才能隔离 skill 相对原文方法的增量。
