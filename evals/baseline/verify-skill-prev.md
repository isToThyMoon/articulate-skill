**结论：没有达标。** 十项验收里没有一项能确认完全满足。"修复字段错误"按现有说明判为未满足。优惠入口、金额变化、支付方式、支付失败恢复这四项都只做到一部分。键盘、触控、窄屏、长文本四类条件，Agent 没交截图、尺寸或测试记录，没法判断；从文字稿里只看到一处风险，就是地址被截断了。

## 逐项对照

| 验收项 | 产物中的证据 | 结论 | 说明与取舍 |
|---|---|---|---|
| 找到优惠入口 | `优惠与发票 ▸（折叠）`，在支付方式和金额明细之间 | 部分满足 | 入口有了，位置也合理。但它是折叠的，又和"发票"放在一行，看标题不知道有没有可用券。折叠省了空间，代价是更难被看到。没有做过用户能否找到的测试。 |
| 理解金额变化 | 明细 `商品 ¥268 配送 ¥0 优惠 -¥20 应付 ¥248`，加起来对得上，支付按钮上也同步显示 ¥248；说明里写"选券后应付数字直接更新，无其他提示" | 部分满足 | 金额怎么构成是清楚的。但金额变的那一刻没有任何反馈：用的是哪张券、省了多少、哪一行变了，都看不出来。折叠状态下已经显示 -¥20，用户不知道这是自动用上的还是自己选的。读屏用户也收不到金额变化的播报。 |
| 确认支付方式 | `支付方式 已选银行卡 修改` | 部分满足 | 只写了"银行卡"这个类别，没写银行和卡号后四位。有多张卡的用户没法确认扣的是哪张。 |
| 修复字段错误 | "错误提示仍在页面顶部汇总" | 未满足（按现有说明） | 在手机上，顶部汇总离出错的字段很远，还可能被软键盘挡住。收货信息又收成了一行摘要加"修改"，用户很难从顶部的提示找到要改的地方。说明里没有提到字段旁边有提示，也没提到点提示能跳过去。 |
| 从支付失败中恢复 | 点击后按钮变成"处理中…"并禁用；失败时弹窗"支付失败，请重试"，关闭后已填内容还在 | 部分满足 | 防止重复提交、保留已填内容，这两点做到了。缺的有四处：没说失败原因；没有"换一种支付方式"的入口；没说钱有没有被扣；没说关掉弹窗后按钮能不能再点。网络超时这类结果不确定的情况下，直接"重试"可能导致重复扣款。 |
| 键盘 | 无 | 材料不足，无法判断 | 以下几点都没有证据：输入框弹出的键盘类型对不对、软键盘会不会挡住输入框或支付按钮、焦点顺序、弹窗打开时焦点能否留在弹窗里、关闭后焦点回到哪里。 |
| 触控 | 无 | 材料不足，无法判断 | "修改"链接和"▸"都是小的点击目标，点击区域多大、彼此隔多远，都没有给。 |
| 窄屏 | 文字稿是"标签 + 值 + 修改"三列 | 材料不足，无法判断 | 没有窄宽度下的截图，看不出三列会不会挤压、换行，支付按钮会不会被推出屏幕。 |
| 长文本 | `张三 · 上海…` | 未满足（有一处实证），其余材料不足 | 结账页的地址是用户要核对的关键信息，截断后看不到区和详细地址。券名很长、银行名很长、金额很大的情况都没有测。 |

## 修改要求（可直接交给 Agent）

1. **优惠入口**：把优惠和发票拆开。优惠这一行在折叠状态下也要显示可用张数，或者已用的券名和减免金额，比如"已用 满200减20 −¥20 ›"。如果系统会自动选券，要明确标出"已自动选择最优券"。验收：未展开时，用户能看出有没有可用券、用了哪张。
2. **金额变化**：选券或换券之后，优惠行显示券名和减免金额；变动的那一行给短暂的视觉提示；应付金额通过状态播报告诉读屏用户（对应 WCAG 4.1.3 Status Messages）。券失效或不满足门槛时，要说明原因。验收：选券、换券、取消券三种操作后，用户不用对比前后数字，就能说出金额为什么变了。
3. **支付方式**：显示银行名和卡号后四位，比如"招商银行 储蓄卡（1234）"。有限额或手续费时一并显示。验收：有两张以上卡的账号能分辨出当前选的是哪一张。
4. **字段错误**：在出错字段旁边显示具体错误和改法。顶部汇总保留，但每条都能点击，点了定位到对应字段并聚焦。错误在收起的收货信息里时，这一行本身要显示错误状态。验收：分别触发手机号格式错误和地址缺失，用户从看到提示到改好，不需要自己找字段；软键盘弹出时，提示和输入框都看得见。
5. **支付失败**：失败提示分情况说明，至少把"未扣款，可重试"和"结果未知，正在确认"分开。提供"重试"和"更换支付方式"两个操作。关闭提示后按钮恢复可点，已填内容保留（这一条已经做到）。结果不确定时，先查订单状态，不要直接让用户再付一次，这也需要后端配合防止重复扣款。验收：模拟余额不足、银行拒绝、网络超时三种情况，逐一检查提示内容和后续路径。
6. **地址截断**：收货地址最多显示两行，保证到区和详细地址的前半段能看到；再长的，点进去能看全部。验收：用 40 个汉字以上的地址，在窄屏下能看出区和街道。
7. **键盘、触控、窄屏、长文本的证据**：按下面补充要求里的第 5 条交回证据。

## 要求本身的缺口

原要求只列了"要检查什么"，没写"怎样算过"，所以 Agent 交回一份文字稿加说明也挑不出形式上的错。建议补上这几条：

- **什么叫"找到"和"理解"**：写清验收方式。例如找 3–5 名目标用户做任务测试，不给提示，看能否找到优惠入口、能否说清应付金额为什么变了；或者约定由审查人按上面第 1、2 条的场景走一遍。
- **四类条件的具体门槛**：下面这些数值来自我记得的公开标准，这次没有联网核对原文，请当作建议参考，按你们平台规范确认后再写成硬性门槛。
  - 窄屏：可参考 WCAG 1.4.10 Reflow 的 320 CSS px 宽度，加上团队主流机型宽度（如 375）。
  - 触控：WCAG 2.5.8 的最低线是 24×24 CSS px；Apple HIG 建议 44×44 pt，Material 建议 48×48 dp，取团队采用的那一套。
  - 键盘：写明是只查手机软键盘遮挡，还是也要查外接键盘或读屏的焦点顺序。
  - 长文本：给出测试用例，比如超长地址、超长券名、超长银行名、6 位以上金额。
- **交付物**：要求 Agent 交回每种状态的截图和逐项检查记录，而不只是文字稿和说明。状态包括默认、选券后、字段报错、处理中、各类失败，窄屏和常规宽度各一套。

补充后的要求可以这样写：

> 审查并修改移动端结账页。验收项：用户未展开时能看出有无可用优惠及已用优惠；选券、换券、取消券后能看出金额变化的原因；能确认具体是哪张卡或哪种支付方式；出现字段错误时，能从提示直接定位到字段并修正；支付失败后能区分是否已扣款，并能选择重试或更换支付方式，已填内容保留。条件检查：320 与 375 CSS px 宽度下无横向滚动、关键信息不被截断到无法核对；点击目标不小于团队采用的最小尺寸（待确认：24 CSS px 或 44 pt）；软键盘弹出时，当前输入框、错误提示和支付按钮可见；弹窗的焦点进出正确；超长地址、券名、银行名、大金额的显示不溢出。交付：每种状态在两种宽度下的截图，以及逐项对照的检查记录（证据位置、结论、没做到的原因）。
