**先看整体**：支付回调是第三方（微信、支付宝、Stripe 等）通知你“这笔钱付了”。第三方收不到你的成功响应就会**重发**。重发这件事改不了，你能做的是让同一个通知处理多少次，结果都和处理一次一样。整段话都在讲这个。

---

### 概念拆解

| 词 | 意思 | 为什么用在这里 |
|---|---|---|
| **上游重试** | 调用你的一方（这里是支付平台）因为超时、网络抖动、没收到 200，把同一个请求再发一遍 | 支付平台一般会重试很多次，重复回调是常态，不算异常 |
| **幂等（业务层）** | 同一操作执行 1 次和 N 次，业务结果一样 | 不做幂等，可能重复加余额、重复发货、重复记账。强调“业务层”，是因为 HTTP 方法层面的幂等（比如 PUT 是幂等的）管不到“订单只能入账一次” |
| **idempotency key（幂等键）** | 标识“这是同一件事”的唯一 ID | 回调场景里通常直接用平台给的交易号或通知 ID。如果是你自己的客户端调你的服务，就由客户端生成 UUID 带上 |
| **持久化去重** | 把处理过的 key 存进数据库或 Redis，下次来了先查 | 放在内存里的话，服务一重启或多实例部署就失效，所以要落盘 |
| **过期策略（TTL）** | 去重记录保留多久后清理 | 不清理的话表会无限增长。保留时长要覆盖上游的最长重试窗口，比如平台最多重试 24 小时，就至少保留 24 小时 |
| **并发竞态（race condition）** | 两个相同请求几乎同时到达，都查到“没处理过”，然后都去处理 | “先查再写”不是原子操作，所以要用**数据库唯一约束**、`INSERT ... ON CONFLICT`、分布式锁，或状态机条件更新（`UPDATE ... WHERE status='待支付'`），保证只有一个请求能成功 |

---

### 以后什么时候主动用这些词

- 碰到**钱、库存、积分、发消息、发货**这类重复执行会出问题的操作，就要想到**幂等**
- 接口会被**重试**时（回调、消息队列消费、网关重试、前端连点提交），就要想到**幂等键 + 去重**
- 设计中有“先查再改”时，就要问一句**并发竞态怎么处理**
- 设计中有存数据防重复时，就要问一句**过期策略是什么**

一句话判断：**会重复到达，而且重复执行有副作用的操作，都要谈幂等。**

---

### 怎么对 Agent 说

> 这个支付回调接口需要**幂等**：上游会**重试**，同一通知可能到达多次。
> 1. 用支付平台的交易号作为**幂等键**；
> 2. 在数据库里**持久化去重**，用**唯一约束**兜底，不要只靠先查后写；
> 3. 处理**并发竞态**：两个相同请求同时到达时，只允许一个执行业务逻辑，另一个直接返回成功；
> 4. 去重记录设置**过期策略**，保留时间覆盖平台最大重试窗口；
> 5. 补测试：重复回调、并发回调，都要验证订单只入账一次。

最后一条最容易被省略。**要求 Agent 写并发测试**，才能确认它真的处理了竞态。
