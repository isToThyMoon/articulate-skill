**拆解范围**：拆的是同事这条评审意见的全文。它要回答的问题是：同一笔支付的回调可能到达不止一次，怎样保证入账和改订单状态只发生一次。引号里是同事的原话，其余是我补充的通用知识。我没有联网核实具体支付渠道的规则。

---

### 1. “上游重试” → “保证业务层幂等”

- **上游重试**：支付渠道发出回调后，如果没收到你的成功响应（比如超时、返回 5xx 或网络中断），通常会再发一次。所以同一笔支付的回调至少到一次，也可能到多次。这是同事整条意见的前提。
- **幂等**：同一个请求执行 1 次和执行 N 次，最终结果一样。“业务层”说的是业务上的效果：订单只改一次状态，余额只加一次，发货只触发一次。只做到“接口没报错”不算。
- **为什么用在这里**：这个回调会改数据，而且涉及钱。重复执行就是重复入账或重复发货。
- **什么时候主动用这个词**：接口满足两个条件时就该提：调用方可能重发，你这边会产生副作用（改数据或触发动作）。常见的有 webhook 和回调、消息队列消费、客户端超时后重试的下单或扣款、用户连续点提交。纯查询接口本来就幂等，不用专门提。
- **换个情境（假设）**：你用消息队列消费“订单已支付”消息，然后给用户发优惠券。消息队列一般也是“至少投递一次”，思路完全一样。
- **对 Agent 说**：
  > “这个接口的调用方在超时或失败时会重发。请保证同一业务请求重复到达时，业务效果只发生一次（只入账一次、只改一次状态），重复请求返回和首次相同的成功结果。请说明你用什么字段识别‘同一请求’。”

### 2. “idempotency key + 持久化去重 + 过期策略”

- **idempotency key（幂等键）**：一个唯一值，用来标识“这是同一次操作”。服务端靠它认出重复请求。
- **需要校准的一点**：原文说“建议客户端带 idempotency key”。但支付回调的调用方是支付渠道，你一般改不了它发什么。通常的做法是直接用渠道给的唯一标识（如支付流水号），或者你自己的商户订单号，当去重键。“客户端生成 key 放在请求里”更适合你自己的 App 调你的下单、扣款接口。建议问一下同事，他指的是哪一端。
- **持久化去重**：“已处理”的记录要存进数据库，不能只放在进程内存里。多实例部署时，另一台机器看不到这台的内存；进程重启后，内存记录也没了。常见做法有两种：给去重键建唯一索引；或者直接看订单状态，已经是“已支付”就不再处理，直接返回成功。
- **过期策略**：去重记录不能无限增长，所以要设保留期。前提是保留期必须长于上游最长的重试时间，具体多长要查你用的支付渠道的文档。如果去重直接靠订单状态，这条基本不需要。
- **换个情境（假设）**：用户在弱网下连点了两次“下单”。这正是由客户端生成 key、放进请求头的典型场景，保留期按客户端的重试时间来定。
- **对 Agent 说**：
  > “用支付渠道回调里的唯一流水号作为去重键（先确认该字段在渠道文档中保证唯一），去重记录落库并建唯一索引。若另设去重表，保留期需长于渠道文档中的最长重试时间，并在方案里写明依据。”

### 3. “并发下两个相同请求同时到达的竞态”

- **竞态**：两个相同的回调几乎同时到达，都先查到“未处理”，然后都去处理。问题出在“先查、再做”之间有空隙，只做持久化去重也挡不住。所以同事单独点出了这一条。
- **判断依据**：检查和写入必须是一个原子动作。常见做法：
  - 先插入去重记录，第二个请求会被唯一索引拦下；
  - 用条件更新 `UPDATE ... SET status='PAID' WHERE id=? AND status='PENDING'`，然后看影响行数是不是 1；
  - 分布式锁也行，但更重。
- **怎么验证**：做并发测试，同时发送多次同一个回调，检查只入账了一次。
- **什么时候主动用这个词**：凡是“先查有没有、没有再写”的逻辑都要想到它，比如扣库存、领券、用户名唯一。
- **对 Agent 说**：
  > “同一回调可能并发到达。去重的检查和写入需要是原子的，不能先查后写。请给出实现方式，并补一个并发测试：同时发送 N 次相同回调，断言只入账一次、订单状态只变更一次。”
