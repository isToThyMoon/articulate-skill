这段评审要解决的问题是：支付平台通知你“用户已付款”时，同一条通知可能到达不止一次。每一次都照常处理，就会出现重复入账、重复发货这类问题。

**1. 上游重试 → 幂等**
- 回调发出后，上游没收到你的成功应答（比如超时、返回 500 或网络断开），就会再发一次。所以同一事件“至少到一次”，但不保证只到一次。
- 幂等的意思是：同一个请求处理一次和处理十次，最终结果一样。
- 同事说的“业务层”幂等，指的是订单状态、余额、发货这些业务结果不能重复发生，光是接口不报错还不够。

**2. idempotency key + 持久化去重 + 过期策略**
- idempotency key（幂等键）是区分“同一件事”的唯一标识。服务端把处理过的键记下来，再遇到同一个键就直接返回上次的结果，不再执行一遍。
- **需要校准的一点（我的推断）**：“让客户端带幂等键”适合你能控制调用方的场景，比如你的 App 调用你的下单接口。支付回调的调用方是第三方支付平台，通常没法让它加你自定义的请求头。这时的幂等键一般用平台给的交易号或通知 ID。另一种做法是用订单状态流转本身去重：只允许“待支付 → 已支付”发生一次。具体用哪个字段，以你接入的平台文档为准。
- “持久化”是说去重记录要放在数据库或 Redis 里。只放在内存里，服务重启或多台实例同时运行时就会失效。
- “过期策略”是在存储成本和安全之间做取舍：记录保留时间必须长于上游的最长重试窗口，否则迟到的重试会被当成新请求再处理一次。如果去重直接靠订单状态，这条记录本来就长期保存，就不存在过期问题。

**3. 并发竞态**
- 两个相同的请求几乎同时到达，都先查一下“有没有处理过”，都查到“没有”，结果都去处理了。这就是“先查再写”的竞态。
- 解决办法是把“判断”和“写入”合成一个原子操作，也就是中途不会被另一个请求插进来。常见做法有：数据库唯一索引插入；带条件的更新，比如 `UPDATE ... WHERE status='待支付'`，再看影响了几行；Redis 的 `SET NX`。
- 验证办法：用并发测试同时发出多个相同请求，确认副作用只发生一次。

**以后什么时候主动用这些词**
只要同时满足两个条件：①同一请求可能到达多次；②处理它会产生副作用（扣钱、发货、发通知）。常见场景有 webhook 回调、消息队列消费、带自动重试的调用、表单被重复提交。

变化情境（假设）：你写的是一个消息队列的消费者。“上游重试”换成“消息重复投递”，幂等键换成消息 ID 或业务单号，竞态照样要处理。如果操作天然幂等（比如“把状态设为 X”、只读查询），就不需要额外去重。

**对 Agent 可以这样说**
> 支付回调接口会因为上游重试而收到重复通知，请让业务处理保持幂等：同一笔支付通知处理多次，订单状态、入账和发货都只生效一次。先确认支付平台回调里哪个字段能唯一标识一次支付（如交易号或通知 ID），用它作为去重依据，并把去重记录持久化（数据库唯一约束或 Redis 均可，附选择理由）。若去重记录设有过期时间，过期时长需长于平台文档写明的最长重试窗口，请注明来源。两个相同通知并发到达时，判断和写入要是原子操作，不能先查再写。重复请求返回与首次一致的成功应答，让上游停止重试。验收：补充一个单测，重复发送同一通知，结果只生效一次；再补充一个并发测试，同时发送多个相同通知，入账或状态流转也只发生一次。
