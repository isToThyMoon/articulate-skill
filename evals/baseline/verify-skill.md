**结论：还没达标。** 5 个用户任务里，"修复字段错误"没做到，另外 4 项只做到一部分。4 个检查条件中，只有长文本能从稿子里看出一点线索；键盘、触控、窄屏三项 Agent 没有交回任何检查记录。你的要求是先审查、再检查这些条件，但 Agent 只交了改版稿和改动说明，没有交检查结果。

**修改要求**

1. **优惠入口**：折叠状态下也要显示优惠情况（例如"已用 1 张，-¥20"或"3 张可用"），用户不展开也知道有没有券可用。验收：让测试者完成"用上优惠券"的任务，不给提示，记录能不能直接找到入口。
2. **金额变化**：选券或取消券后，用户在当前屏幕内就能看到减了多少、应付变成多少，支付按钮上的金额同步更新；同时说明 -¥20 是怎么来的。验收：在最窄的目标屏幕上展开优惠区选券，看同一屏里能不能看到变化，按钮金额和应付金额是否一致。
3. **支付方式**：摘要里显示能认出具体哪张卡的信息（银行名 + 尾号）。验收：只看这一行，用户就能说出这次会扣哪张卡。
4. **字段错误**：每个出错的字段旁边写明具体问题；顶部汇总的每一条都能点，点了跳到对应字段并把光标放进去；出错字段在折叠区或摘要行里时自动展开。验收：页面停在底部时点"支付"，故意漏填地址，看用户能不能不靠自己滚动就找到并改好，改完后错误提示消失。
5. **支付失败**：失败提示要说清大致原因和下一步能做什么（重试、换支付方式），关闭弹窗后按钮恢复可点；结果不确定时，先查订单状态，再决定让不让重试。验收：分别模拟银行拒付、网络超时、结果未知三种情况，每种都要么能完成支付，要么得到明确状态，而且不会重复扣款。
6. **长文本**：付款前能看到完整的收货地址（比如点一下展开）；超长姓名、地址、券名、错误文案都不能挡住金额和支付按钮。验收：用最长的样例在最窄的目标宽度下截图检查。

**要求本身也有缺口**：没写"能找到""能理解"用什么证明（比如做任务测试、找几个人），没定窄屏以多宽为准（建议给具体值，比如 320 和 360 宽），也没说"键盘"是指软键盘遮挡，还是外接键盘或读屏软件的焦点顺序。建议把这三点补进要求，并要求 Agent 对每个检查条件交回截图或检查记录。不然下一轮，键盘、触控、窄屏这三项还是没法判断。
