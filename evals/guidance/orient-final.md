下面先给出面向网页与移动产品的紧凑 UI 设计地图，再给出核心概念的理解顺序。本次仅使用内化知识，没有联网核查；平台规范、无障碍标准版本和团队约定在实际项目中仍需确认。

UI 设计解决的是：如何把内容、操作和系统状态组织成用户看得懂、找得到、用得成、出错后能恢复的界面。这里覆盖信息组织、交互、视觉表达、组件、适配与评价；暂不展开品牌设计、复杂动效、用户研究方法和具体设计工具。

骨架关系是：

> 用户目标约束任务流；任务流决定需要什么内容和状态；信息架构组织内容；视觉层级与操作提示表达优先级；组件实现一致行为；反馈、无障碍和响应适配保障不同条件下仍可完成任务；评价证据再推动修订。

## 八类领域地图

| 类别 | 紧凑地图 |
|---|---|
| **核心实体 Entities** | 用户与目标；页面、内容与导航；操作与组件；默认、加载、空、成功、错误等状态；设备与输入方式。用户目标约束页面优先级，状态决定组件在任务流中的实际行为。 |
| **核心概念 Concepts** | **任务流**描述完成目标的步骤与分支；**信息架构**组织内容和入口；**视觉层级**表达重要性；**可供性与操作提示**让人看出怎样操作；**反馈与恢复**说明结果并处理失败；**渐进披露**在可发现性与当下负担之间取舍。 |
| **常见实用术语 Vocabulary** | Primary/Secondary Action（主次操作）、CTA（关键行动入口）、Design Token（命名后的设计决定）、Breakpoint（布局切换条件）、Empty State（空状态）、Focus State（键盘焦点状态）、Information Scent（入口指向目标的线索）。这些词分别指向优先级、系统化、适配、状态与可发现性。 |
| **工作流 Workflow** | 定义用户与任务 → 画正常及异常流程 → 组织内容与导航 → 做线框和视觉层级 → 补齐组件状态与响应规则 → 原型验证 → 交付实现 → 根据证据返工。发现分类错误回到信息架构，发现操作死路回到任务流，不用视觉润色掩盖结构问题。 |
| **常见产物 Artifacts** | 信息架构图、任务流、线框图、高保真稿、交互原型、组件库、设计 token、状态矩阵、响应规则、内容规范、测试记录和设计决策说明。不同产物服务不同决策；高保真稿不能替代流程和状态定义。 |
| **评价 Evaluation** | 检查任务成功、可发现性、可理解性、操作成本、错误恢复、视觉层级、一致性、无障碍和多尺寸适配。评价要落到观察：用户在哪里停顿、误判、失败或漏看；“更高级”“更清爽”本身不是验收证据。 |
| **失败模式 Failure modes** | 多个元素争夺焦点；装饰替代信息结构；同形组件行为不同；只设计正常状态；重要功能被过度隐藏；只靠颜色表达状态；单屏好看但长文本或窄屏失效；用个人偏好代替任务证据。症状出现时先定位对应结构、流程或组件原因。 |
| **标准与框架 Standards / frameworks** | WCAG 与 WAI-ARIA 用于网页无障碍；Apple HIG 和 Material Design 提供平台指导；ISO 9241 涉及人机交互与以人为中心设计；团队设计系统约束当前产品组件和语言。它们的具体版本、条款与适用范围本次未联网核验，实际使用前需查原文。 |

## 贯穿案例：移动端结账页

以下是教学假设。

现状：结账页同时展示地址、配送、优惠券、积分、支付、发票、商品明细和推荐商品；上下各有一个醒目的提交按钮；错误只在页面顶部汇总。目标是让用户确认订单并安全完成支付。

从任务流看，确认地址、支付方式和最终金额是主任务；推荐商品不是结账必要信息。信息架构可整理为“收货与配送—支付方式—优惠与发票—费用汇总—支付”。视觉层级应突出最终金额和主要操作；优惠等次级设置可以展开，但入口必须可发现，金额变化必须立即反馈。错误应出现在对应字段附近，提交后应显示处理中状态以防重复支付，失败后保留已填内容并给出恢复路径。

一个产物片段：

```text
确认订单

收货与配送    张三 · 上海…       修改
支付方式      已选银行卡          修改
优惠与发票    已优惠 ¥20           展开

商品 ¥268  配送 ¥0  优惠 -¥20
应付 ¥248

[ 支付 ¥248 ]
```

可交给 Agent 的要求：

> 请审查这个移动端结账页。先建立主要任务流，区分完成支付所需信息、次级设置和无关内容；再检查信息分组、视觉层级、操作提示、金额反馈，以及加载、校验、支付失败和重复提交状态。不要预设用更多卡片、渐变或动效。交付结构调整说明、关键线框和状态矩阵，并说明每项改动解决哪个可观察问题。验收时检查用户能否找到优惠入口、理解金额变化、确认支付方式、修复字段错误并从支付失败中恢复；同时检查键盘、触控、窄屏和长文本条件。缺少真实页面、平台或设计系统时，把结论写成待验证项或条件化方案。

教学模拟评价：测试者找到了“优惠与发票”，但使用优惠后漏看总额变化；因此保留该入口与分组，修订金额反馈——在入口旁显示优惠金额，并在费用汇总中突出变化来源。若仍被漏看，应返回视觉层级和反馈设计，而不是继续隐藏或增加装饰。

## 核心概念的理解依赖顺序

这是一条教学顺序；其中有些是互相约束的概念组，不是严格的单向先修链。

| 顺序 | 概念组 | 含义与依赖理由 | 可用于要求 Agent |
|---|---|---|---|
| 1 | **用户目标与任务** | 先确定用户在什么情境下要得到什么结果；它为后续结构和评价提供方向。 | “先写出主要用户目标和次要目标，再判断界面问题。” |
| 2 | **任务流与系统状态** | 任务流描述步骤与分支，状态说明每一步是否可继续、成功或需要恢复；两者依赖明确目标。 | “列出正常路径，以及等待、取消、错误、权限不足和重试路径。” |
| 3 | **信息架构与内容优先级** | 根据任务所需信息决定分类、命名、顺序和导航；错误分类无法靠视觉样式补救。 | “说明哪些内容应常显、按需展开或移出主流程，并给出任务依据。” |
| 4 | **分组与视觉层级** | 分组表达归属，视觉层级表达先后和重要性；它们应呈现信息结构，而非替代结构决策。 | “指出用户第一眼、第二眼和行动前会注意什么，核对是否符合任务顺序。” |
| 5 | **可供性、操作提示与可发现性** | 用户需要看出哪里能操作、怎样操作、将得到什么；它依赖清楚的入口含义和足够的视觉权重。 | “找出可能被误认为可点击或不可点击的元素，并检查标签能否预测结果。” |
| 6 | **反馈、错误预防与恢复** | 对每次操作说明系统状态，降低错误风险，并在失败后带用户回到原任务。 | “说明操作收到、处理中、成功和失败分别怎样表达，以及失败后保留什么。” |
| 7 | **一致性、组件与设计系统** | 把已经明确的语义和行为沉淀成可复用规则；过早组件化会复制未经验证的问题。 | “优先复用现有组件；新增变体时说明现有模式为何不适用。” |
| 8 | **渐进披露与认知负担** | 决定当前展示什么、以后展示什么；减少当下信息可能损害可发现性，因此依赖任务优先级和入口设计。 | “列出必须立即可见和可以展开的信息，并检查隐藏后用户是否仍知道它存在。” |
| 9 | **无障碍与多种输入** | 语义、焦点、对比、缩放、触控和非颜色提示应贯穿结构与组件，不是视觉稿完成后的附加项。 | “同时检查键盘顺序、焦点、语义、对比、动态字号、触控区域和状态冗余。” |
| 10 | **响应式设计与内容韧性** | 根据空间、文本长度和输入方式重排结构，同时保持任务优先级和功能完整。 | “说明窄屏、长文本和不同输入方式下什么会重排，什么必须保持。” |
| 11 | **评价证据与取舍** | 用任务表现和观察判断设计；它依赖前面已经定义的目标、流程与质量要求，也要处理效率、可发现性等目标冲突。 | “逐项说明改动解决什么问题、怎样验证，以及可能牺牲什么。” |

建议先学前四组：**用户目标 → 任务流 → 信息架构 → 分组与视觉层级**。它们构成 UI 设计的决策骨架；组件、视觉风格和工具操作应建立在这套骨架之上。
