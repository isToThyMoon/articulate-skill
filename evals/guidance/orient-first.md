下面是一张面向产品界面设计的紧凑 UI 设计地图。它覆盖网页与移动应用的通用界面设计，重点是信息组织、交互表达、视觉系统和质量判断；暂不展开品牌设计、用户研究、复杂动效、游戏 UI 和具体设计工具。

本次按你的要求离线整理，仅使用内化知识，没有核查外部资料。因此它适合作为候选知识结构；具体平台规范、无障碍要求版本和团队约定，实际使用前仍需确认。

UI 设计的骨架可以概括为：

> 用户带着目标进入界面 → 界面组织信息与操作 → 视觉层级提示先看什么、先做什么 → 组件和反馈帮助用户完成任务 → 状态与错误处理保障过程可恢复 → 通过可用性、无障碍、一致性和业务结果判断设计。

## 八类领域地图

### 1. 核心实体 Entities

- **用户与用户目标**：界面服务的对象以及他要完成的任务。用户目标决定什么信息应优先出现。
- **页面、区域与内容**：页面承载任务，区域组织相关信息，内容提供判断和操作依据。
- **操作与导航**：按钮、链接、菜单、表单等让用户改变状态或前往其他位置。
- **组件**：可复用的界面单元，如输入框、对话框、标签页和卡片。组件通过一致行为降低重新学习成本。
- **状态**：默认、悬停、聚焦、加载、成功、错误、空数据、禁用等。界面是否完整，常取决于主流程之外的状态。
- **设备与输入方式**：屏幕尺寸、触摸、鼠标、键盘和辅助技术会约束布局与交互。

### 2. 核心概念 Concepts

- **信息架构（Information Architecture）**：决定内容怎样分类、命名和导航。它约束页面结构，视觉样式无法弥补错误的分类。
- **任务流（Task Flow）**：用户为完成一个目标经过的步骤、决策和反馈。它用于发现多余步骤、死路和恢复缺口。
- **视觉层级（Visual Hierarchy）**：通过位置、尺寸、对比、留白和字重表达重要性。它应反映任务优先级。
- **可供性与操作提示（Affordance / Signifier）**：让用户看出什么可以操作以及如何操作。视觉像按钮却不能点击，或可以点击却没有提示，都会造成误判。
- **分组与邻近（Grouping / Proximity）**：通过空间、边界和对齐表达哪些内容属于一组。分组决定用户怎样理解结构。
- **一致性（Consistency）**：相同含义使用相同表达和行为。它依赖组件、规则和内容语言的一致，而不只是颜色统一。
- **渐进披露（Progressive Disclosure）**：先展示当前任务需要的信息，再按需展开复杂内容。它降低当下负担，但可能牺牲可发现性。
- **反馈与系统状态可见性**：操作后及时说明正在发生什么、是否成功以及下一步是什么。
- **错误预防与恢复**：优先减少错误发生；发生后提供原因、影响和恢复路径。
- **无障碍（Accessibility）**：让不同感知、运动和认知能力的用户都能理解和操作界面。它会影响语义结构、焦点、对比和输入方式。
- **响应式设计（Responsive Design）**：界面根据可用空间重排、收缩或切换结构，而非简单等比例缩小。

### 3. 常见实用术语 Vocabulary

- **Primary / Secondary Action**：主要操作与次要操作，指当前情境下的行动优先级。
- **CTA（Call to Action）**：希望用户采取的关键行动；并非每个按钮都是主要 CTA。
- **Design Token**：保存颜色、字号、间距、圆角等设计决定的命名值，用来连接设计规则与实现。
- **Breakpoint**：响应式布局发生结构变化的条件，通常与可用空间有关。
- **Empty State**：没有内容时的状态，应解释现状，并在适当时提供下一步。
- **Skeleton / Loading State**：加载期间用于表达结构或进度的状态；使用不当会制造虚假速度感。
- **Modal / Dialog**：覆盖当前界面的临时层，适合需要集中处理且明确结束的任务。
- **Information Scent**：标签或入口让用户判断“这里是否通向我要找的内容”的线索。
- **Cognitive Load**：理解、记忆和决策占用的认知资源；减少视觉元素不一定等于减少认知负担。
- **Interaction Cost**：完成任务所需的注意、判断、输入和操作成本。
- **Focus State**：键盘或辅助技术当前操作位置的可见表现。
- **Touch Target**：触控操作的有效点击区域，不能只按图标的视觉尺寸判断。

### 4. 工作流 Workflow

1. **定义任务与边界**：明确用户、场景、主要目标、业务目标和技术限制。
2. **组织信息**：确定内容分类、页面层级、标签和导航关系。
3. **绘制任务流**：画出正常路径、分支、取消、错误和恢复。
4. **建立线框结构**：先决定内容顺序、分组和操作位置，暂不依赖精细视觉。
5. **设计视觉层级**：用排版、间距、颜色和对比表达结构与优先级。
6. **补齐交互状态**：覆盖加载、空、错误、成功、禁用和不同输入方式。
7. **应用组件与设计系统**：复用已有规则，必要时说明新增模式的理由。
8. **制作原型并验证**：用代表性任务观察用户能否发现、理解和完成操作。
9. **交付与实现核对**：提供规格、状态、响应规则和验收条件，并检查实现偏差。
10. **根据证据迭代**：区分理解问题、交互问题、视觉问题和实现问题，再返回相应环节。

### 5. 常见产物 Artifacts

- **站点地图或信息架构图**：表示页面和内容之间的层级关系。
- **用户流或任务流图**：表示步骤、决策、失败和恢复路径。
- **线框图**：用于检查结构、顺序和操作布局。
- **高保真界面稿**：呈现最终视觉与组件组合。
- **交互原型**：模拟关键操作和状态变化，用于评审或测试。
- **组件库与设计系统**：沉淀可复用组件、设计 token 和使用规则。
- **内容规范**：约定标签、按钮文案、错误信息和语气。
- **设计规格与状态矩阵**：向开发说明尺寸、行为、响应规则及各种状态。
- **可用性测试记录**：记录任务、观察、证据和问题，不只记录用户偏好。
- **设计决策说明**：保存问题、选项、取舍和选择依据。

### 6. 评价 Evaluation

- **任务成功**：用户能否完成主要任务，在哪一步失败或需要帮助。
- **可发现性**：用户能否找到入口，并从标签和位置判断它的作用。
- **可理解性**：用户能否理解内容、状态和操作后果。
- **效率**：完成任务需要多少不必要的步骤、输入和等待。
- **错误与恢复**：错误是否得到预防，发生后是否知道原因和恢复办法。
- **视觉层级**：最重要的信息和操作是否先被注意，次要内容是否形成稳定层次。
- **一致性**：相同含义是否使用相同组件、文案和反馈。
- **无障碍**：键盘操作、焦点顺序、语义、对比、缩放和辅助技术是否可用。
- **响应适配**：不同空间下是否保持内容优先级和操作完整性。
- **主观品质**：界面是否符合品牌语气、类型预期和目标用户；应结合对照样本说明理由，不能只说“高级”或“好看”。

评价维度会相互制约。例如，渐进披露可以降低首屏负担，却可能降低功能可发现性；更强的视觉对比可以突出主要操作，也可能让其他必要信息被忽略。

### 7. 常见失败模式 Failure Modes

- **多个元素同时争夺注意力**：标题、卡片、颜色和按钮都很突出。先检查任务优先级，再调整视觉层级。
- **装饰替代结构**：通过阴影、渐变和卡片包装内容，却没有清楚的分类和顺序。
- **组件外观相同但行为不同**：造成错误预期。检查组件语义和交互规则。
- **正常流程完整，边界状态缺失**：加载、空数据、错误和权限不足时界面失效。
- **只为单一屏幕设计**：窄屏溢出、长文本破坏布局、触控目标过小。
- **用占位文本代替标签**：输入后提示消失，用户难以确认字段含义。
- **用颜色作为唯一信号**：状态对部分用户不可辨认，也缺少文字或图形冗余。
- **确认框滥用**：频繁打断流程，用户形成无意识确认；高风险操作反而没有真正保护。
- **渐进披露过度**：重要能力被藏得太深，用户不知道入口存在。
- **只统一视觉，不统一决策**：颜色和圆角一致，但相同场景使用不同操作、状态和术语。
- **把个人偏好当作可用性证据**：评审集中在“喜欢哪版”，没有检查实际任务。

### 8. 标准与框架 Standards / Frameworks

UI 设计同时受到正式标准、平台指南和团队系统约束：

- **WCAG**：网页内容无障碍指南，用于检查可感知、可操作、可理解和兼容性；具体版本与合规级别需联网确认。
- **WAI-ARIA**：补充网页界面组件的无障碍语义；错误使用可能比不使用更糟。
- **Apple Human Interface Guidelines**：面向 Apple 平台的交互与视觉指南。
- **Material Design**：Google 的设计系统与组件指导，不是所有 Android 产品都必须照搬其视觉风格。
- **ISO 9241 系列**：涉及人机交互、人体工学和以人为中心设计；具体条款需要查原文。
- **团队设计系统**：规定产品自己的组件、token、内容与交互模式，其适用性高于通用风格偏好。
- **启发式评估**：用系统状态、现实匹配、用户控制、一致性、错误预防等原则发现问题；它是检查框架，不能代替真实用户证据。

## 贯穿案例：优化移动端结账页

以下是教学假设。

现状：移动端结账页同时展示收货地址、配送选择、优惠券、积分、支付方式、发票、商品明细和推荐商品。页面顶部和底部各有一个醒目的“提交订单”，错误只在页面顶部集中显示。

目标：让用户更容易检查订单并完成支付，同时避免漏看价格变化和字段错误。

先从任务流看，核心任务是确认订单信息并支付；推荐商品不属于完成任务的必要步骤。信息架构因此将页面组织为“收货与配送—支付—费用汇总—提交”，推荐内容降级或移出结账主流程。

再用视觉层级表达这一顺序：费用总额和唯一的主要操作保持突出；优惠券、积分和发票作为可展开的次级设置；商品明细可以折叠，但价格变化必须在费用汇总中立即反馈。这里使用渐进披露，是为了降低同时需要判断的信息量，前提是入口标签明确且展开后的变化可见。

状态设计还需补齐：

- 地址或支付信息缺失时，在对应字段附近显示原因和修复方法。
- 提交后进入明确的处理中状态，避免重复支付。
- 价格改变时，在总额附近解释变化来源。
- 支付失败时保留用户已经填写的内容，并提供重试或更换方式。
- 键盘焦点按视觉和任务顺序移动，错误发生后能定位到对应区域。

一个简化线框片段可以是：

```text
确认订单

收货与配送
张三 · 138… · 上海…
明天送达                         修改

支付方式
● 已选银行卡                     修改

优惠与发票
优惠券、积分、发票               展开

费用明细
商品                            ¥268
配送                              ¥0
优惠                            -¥20
应付                            ¥248

[ 支付 ¥248 ]
```

模拟验收时，让测试者完成“检查地址、使用一张优惠券并支付”的任务。观察他是否找到优惠入口、是否注意总额变化、是否清楚当前支付方式，以及错误后能否恢复。如果用户普遍找不到优惠入口，应回到标签和信息层级；如果能找到却不理解金额变化，应修正反馈；如果只有窄屏出现遮挡，则返回响应布局或实现检查。

可交给 Agent 的要求是：

> 请审查并优化这个移动端结账页。先根据页面内容建立主要任务流，区分完成支付所需的信息、次级设置和无关内容；再检查信息分组、视觉层级、主要操作、金额反馈以及加载、校验、支付失败和重复提交等状态。不要预设采用更多卡片、渐变或动效。
>
> 设计时保证用户能确认收货、支付方式和最终金额，优惠或费用变化能及时解释，字段错误能在对应位置修复。主要操作的数量与位置应由实际滚动长度和平台行为决定，不要未经证据固定为一个或两个。
>
> 请交付结构调整说明、关键页面或线框、状态矩阵，以及每项改动对应的问题。验收时检查任务完成、入口可发现性、金额变化理解、错误恢复、键盘与触控操作、窄屏和长文本适配。若缺少真实页面、目标平台或现有设计系统，请把相关结论写成待验证项或条件化方案。

## 核心概念的理解依赖顺序

这是一条建议学习路径。部分概念互相影响，并非严格线性先修关系。

1. **用户目标与任务**

   含义：用户在具体情境中希望得到的结果，而不是界面上某个按钮的名称。

   先学原因：它决定内容、操作和评价标准。没有目标，所谓“简洁”“高级”或“突出”都缺少方向。

   可用于要求 Agent：  
   “先说明这个页面服务的主要用户目标和次要目标，再判断界面问题。”

2. **任务流与系统状态**

   含义：完成目标所经历的步骤、决策和反馈，以及每一步可能处于的状态。

   依赖关系：任务流以用户目标为起点；状态说明每一步是否可继续、成功或需要恢复。

   检查问题：  
   “正常路径之外，取消、等待、错误、权限不足和重试怎样处理？”

3. **信息架构与内容优先级**

   含义：内容如何分类、命名、排序和连接。

   依赖关系：任务流告诉你用户何时需要什么信息，信息架构再决定它放在哪里、叫什么。

   可用于要求 Agent：  
   “按完成任务所需的先后关系重组内容，并说明哪些信息应常显、折叠或移出主流程。”

4. **分组与视觉层级**

   含义：分组表达内容关系，视觉层级表达重要性和阅读顺序。

   依赖关系：它们应呈现既有的信息结构，不能代替信息架构。若业务优先级没定，单纯放大按钮只是猜测。

   检查问题：  
   “用户第一眼、第二眼和准备操作时分别会注意什么？这是否符合任务顺序？”

5. **可供性、操作提示与可发现性**

   含义：用户能否看出什么可操作、怎样操作，以及入口会通向什么。

   依赖关系：信息架构决定入口含义，视觉层级决定入口是否被注意，操作提示决定用户是否敢于行动。

   可用于要求 Agent：  
   “检查每个可交互元素是否能被识别，标签是否能预测结果，并列出可能被误认为可点击或不可点击的元素。”

6. **反馈、错误预防与恢复**

   含义：操作后显示系统状态，在错误前降低风险，错误后帮助用户继续。

   依赖关系：只有明确任务步骤和操作含义，才能设计正确反馈；错误处理应返回原任务，而不是形成死路。

   检查问题：  
   “用户如何知道操作已收到、正在处理、成功或失败？失败后保留了什么？”

7. **一致性、组件与设计系统**

   含义：把反复出现的语义和行为沉淀成稳定组件及规则。

   依赖关系：组件应复用已经验证的交互决策。过早组件化会把未经验证的问题复制到更多页面。

   可用于要求 Agent：  
   “优先复用现有组件；若新增或变体化，说明现有模式为何不能表达当前语义。”

8. **渐进披露与认知负担**

   含义：控制同时呈现的信息和决策，把复杂性安排到适当时机。

   依赖关系：它需要任务流、内容优先级和可发现性作为前提；隐藏内容可以减轻当下负担，也可能增加查找成本。

   检查问题：  
   “哪些信息当前必须看见，哪些可以按需展开？隐藏后用户还知道它存在吗？”

9. **无障碍与多种输入方式**

   含义：让界面对不同能力、设备和操作方式保持可感知、可理解和可操作。

   依赖关系：无障碍贯穿结构、组件、状态和视觉表达，不是完成视觉稿后的附加检查。

   可用于要求 Agent：  
   “同时检查语义结构、键盘顺序、焦点、对比、缩放、触控区域和非颜色状态提示。”

10. **响应式设计与内容韧性**

    含义：当空间、文本长度和输入方式变化时，界面仍保持任务优先级和功能完整。

    依赖关系：只有理解内容优先级和组件行为，才能决定重排、收缩、折叠还是切换模式。

    检查问题：  
    “窄屏、横屏、长文本、动态字号和不同输入方式下，哪些结构发生变化，哪些优先级必须保持？”

11. **评价证据与取舍**

    含义：用任务表现、观察和实现结果判断设计，而不是把个人偏好当结论。

    依赖关系：评价需要前面定义的目标、流程、状态和质量要求；不同指标可能冲突。

    可用于要求 Agent：  
    “逐项说明改动解决什么可观察问题、如何验证，以及可能牺牲什么。”
