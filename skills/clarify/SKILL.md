# Clarify

把用户对一个具体任务的普通表达，追问成专业人士会怎样描述这个任务：关注哪些对象和状态，用哪些概念解释现象，受什么约束，怎样验收。结果是一份任务模型，让执行者需要猜测的内容尽量少。专业词是索引；模型的价值在于目标、依据、范围和验收都已说清。

开始时读取 [共同方法](references/foundation.md)。用户带来产物要求检查时，从第 4 步开始。

## 1. 锚定意图

读取原话和有关材料，分出：想改变的结果、涉及的对象、已观察到的现象、偏好、原因猜测和预设方案。只有命令没有内容时，请用户给一句想说清楚的话。

完成条件：能用一句话复述用户想改变什么结果，并列出会改变做法的关键歧义。原话已经准确时，补真实缺口后直接交付。

## 2. 追问关键区别

用八类找缺口：哪一类的空白会让执行者走向不同做法（对象和状态不明、现象有几种机制解释、约束未知、验收无从判断），就先问哪一类。

每轮只问一个核心问题：给两三个具体解释或对照，附上专业人士对各自的叫法，说明选哪一个会改变什么，然后等待真实回答。回答后用五层讲清选中的概念：叫什么，解释什么问题，和哪些因素相关，在任务哪一步起作用，怎样检查。

例：“把这个接口写得健壮一点”可能指网络重试时业务只执行一次（幂等）、依赖超时后仍能给出结果（降级）、异常输入得到明确错误（输入校验）。问用户更接近哪种。回答“重试时只扣一次款”后，下一问转向对象与状态：哪些操作有副作用，重复请求靠什么识别。

把 grill 的力度用在有后果的假设、矛盾和取舍上；个人偏好本身可以作为目标。用户不确定时提供具体对照，缺少实物时保留候选解释。区分目标和手段：目标是要改变的结果，手段是服务目标的候选做法。

“高级”“专业”等评价词尚未澄清时，保留原词作为待解释目标；写进任务说明时只带它的推导来源：“方向从现有材料、受众与主要目标推导，先提出 2–3 个候选供确认”，具体方案名只出现在这些候选里。

**收束条件**：目标、对象和关键区别已明确，剩余未知可写成检查任务或条件化方案。用户要求直接整理时，立即用现有信息走这条收束路径。

## 3. 写成任务模型

按需要交付两部分，短任务可合并为一段：

- **专业说法**：用专业人士的表达重述用户的意思，关键术语旁注明对应的原话。
- **任务说明**：交给 Agent 的可执行版本。

用户只要其中一部分时，只交那一部分；只交任务说明时，关键术语的含义写进说明本身。

任务说明先写目标与优先级、依据的材料与未知项，再用八类检查要素是否齐全：

| 八类 | 任务说明中要交代 |
|---|---|
| 实体 | 操作对象、范围和相关状态（正常、空、加载、失败等） |
| 概念 | 起作用的机制，以及它和用户所说现象的对应 |
| 术语 | 执行者会用到的专业说法 |
| 工作流 | 这次是诊断、探索还是实施；先做什么，何时停下确认 |
| 产物 | 交付什么 |
| 评价 | 可观察结果、测试、对照样本或测量；数值注明依据或建议性质 |
| 失败模式 | 相关边界与副作用，写成要守住的状态及检查办法 |
| 标准与框架 | 必须沿用的规范、约束和权限 |

这是交付前的检查，详细程度以支持正确决策为准。呈现时用自然段或必要的列表；缺项写成待确认、待检查或不适用。额外的方案建议另行简述，方便用户选择。

完成条件：单独读一次任务说明，它符合共同方法中的“可移交”——执行者能找到目标、依据、下一步和验收办法；新增约束有依据，未知前提保留条件。证据不足时交付诊断任务。

## 4. 验收产出

用同一份任务模型检查产物。用户只给出笼统评价、没有明确要求时，先用第 1–3 步整理出验收项，再检查。

先给总体结论，再逐项对照评价与失败模式：每项一行，写证据（产物中的位置或片段）、结论（满足、部分满足、未满足、材料不足无法判断）和一句理由。具体改法只写在随后的修改要求里，只列未满足和部分满足的项，每项一句目标状态、一句验收办法。任务说明本身有缺口时，用一两句指出；用户需要时再给修订后的任务说明。

完成条件：每个验收项都有证据落点和结论；每个未满足或部分满足的项有一条可移交的修改要求。

用户明确要求保存表达或调用已有知识库时，读取 [知识库](references/lexicon.md)。
